# ADR-0024: Third-party licence notices ship inside the release archives

- [Status](#status)

- [Decision](#decision)
- [Consequences](#consequences)
- [References](#references)

## Status

Accepted (2026-07-25). Extends the downstream-packager contract in
README "For downstream packagers"; the archive layout gains a fourth
file, which is a contract change per that section.

## Context

The published archives contain a statically linked binary. Everything
the binary links — around a hundred crates across all targets — comes
with an attribution obligation: MIT, BSD-2-Clause, BSD-3-Clause,
Apache-2.0, Unlicense, Zlib, Unicode-3.0 and Unicode-DFS-2016 all
require the copyright notice and licence text to be reproduced when the
work is redistributed in binary form. Until now the archives carried a
single `LICENSE` file, covering this project's own MIT-licensed code
only, so the obligation was unmet for every dependency.

The consumer that redistributes the binary further,
[`markdown-org-vscode`](https://github.com/VitalyOstanin/markdown-org-vscode),
inherits the same obligation: it bundles the prebuilt binary inside its
VSIX. It cannot satisfy it on its own without keeping a hand-copied list
that goes stale the moment the pinned extractor version moves.

Three options were considered:

1. A notice file maintained by hand in each consumer. Rejected: it goes
   stale silently, and staleness is invisible until someone audits it.
2. Generation at package time on every runner. Rejected: packaging runs
   on Linux, macOS and Windows, while generation needs cargo plus the
   unpacked crate sources; three runner OSes would have to reproduce the
   same bytes for the archives to stay reproducible.
3. A generated file committed to this repository, shipped in the
   archives, and regenerated in CI to prove it is current.

`cargo about` was not adopted: it would add a build-time tool to install
on every machine that produces the file, for output this project can
produce from `cargo tree` plus `cargo metadata` directly.

## Decision

`THIRD-PARTY-LICENSES.txt` is generated by
`scripts/generate-third-party-licenses.sh`, committed to the repository,
and staged into every release archive next to `README.md` and `LICENSE`.

- The crate list is the union of the normal dependency graph over every
  target (`cargo tree --edges normal --target all`). One file therefore
  covers all four archives, at the cost of naming crates a given binary
  does not link (other platforms', and proc-macro crates used only
  during the build). Over-inclusion is the safe direction for an
  attribution notice.
- Every licence file a crate ships (`LICENSE*`, `LICENCE*`, `COPYING*`,
  `NOTICE*`, `UNLICENSE*`) is reproduced in full. Identical texts are
  emitted once and referenced by index, which is what keeps the file at
  a few hundred kilobytes rather than a few megabytes.
- A crate that ships no licence text at all fails the generator. Such a
  dependency needs a decision, not a silent omission.
- The file carries no version of this project, so it changes only when
  the dependency graph does — a release bump does not make it stale.
- `scripts/verify-archive.sh` requires the file, so an archive without
  it cannot be published.
- CI regenerates the file and fails when the result differs from the
  committed copy, and `cargo deny check licenses` (see `deny.toml`)
  fails when a dependency introduces a licence outside the allow-list.

## Consequences

- A dependency change is a two-part commit: the lockfile change and the
  regenerated notice file. CI names the script to run when they diverge.
- The allow-list in `deny.toml` is deliberately narrow — exactly the
  licences present in the graph. Adding a dependency with a new licence
  is a conscious decision recorded in that file, not a silent import.
- Downstream packagers get the notices in the archive, so redistributing
  the binary no longer requires them to reconstruct the list. The VS
  Code extension picks the file up next to the binary it downloads.
- Adding a fifth file to the archive stays a contract change: the
  `required` list in `scripts/verify-archive.sh` and the layout tree in
  the README are the two places that define it.
